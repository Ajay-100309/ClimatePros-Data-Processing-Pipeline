Use Case C · Parts Finder · System Architecture Brief

A flat search over dispatch history, no case-clustering step required

A technician logs what's wrong with a dispatch. Parts Finder turns that description into a search, finds a wide pool of similar jobs directly from history, and suggests which parts they'll probably need. The existing case-clustering pipeline keeps running for its own root-cause reporting, but this design no longer depends on it. Testing showed a wider direct search beats routing through that pipeline. A technician signs off before anything gets acted on.

Out of scope: parts pricing, purchase orders, inventory management. This system suggests parts for a technician to review; pricing and ordering stay with the existing tools.

Where this stands: the earlier version of this design routed through the case-clustering pipeline. Direct testing (Section 03) showed a plain, wider search beats that approach, so the case pipeline was dropped from this system's live path entirely. Section 02 covers how the matching works now; Section 05 covers what's next.

01

System Architecture

One vector store handles both the historical index and every live query. A new dispatch is compared directly against a wide pool of past dispatches, no case-matching step in between. A technician reviews the result, and their confirmation becomes part of the record the next prediction draws on.

02

How the Matching Actually Works

This is the mechanism underneath the diagram above: what text becomes searchable numbers, which model does that, where those numbers live, and the exact steps from a new dispatch to a ranked parts list.

What gets embedded

Text usedModelStored in
Historical dispatch
embedded once, when it's cleaned		 The root-cause sentence extracted from technician notes, plus the raw reason field as a backup bge-m3, 1,024 numbers, document mode Azure AI Search, along with whatever real part was used, if any was recorded
New dispatch
embedded fresh, every request		 The technician's live description, typed in at request time bge-m3, 1,024 numbers, query mode Not stored, generated per request and discarded after

bge-m3 is the model specified for production. Every accuracy number in Section 03 was produced with nomic-embed instead, 768 numbers per dispatch, because that's the model the existing case pipeline already has running. The matching mechanism is identical either way; swapping bge-m3 in is one of the next steps in Section 05.

From a new dispatch to a ranked parts list

  1. Embed the description. The technician's text becomes 1,024 numbers using bge-m3 in query mode.
  2. Search. Those numbers are compared against every historical dispatch's numbers already in Azure AI Search, using cosine similarity, a standard measure of how alike two lists of numbers are.
  3. Retrieve. The 100 closest historical dispatches come back directly. No case lookup, no case-matching step.
  4. Score. Among those 100, whichever ones have a real recorded part contribute to the score, weighted by how close a match they were, plus a smaller fixed contribution from how often that part is used across all of history. That second term catches a part that's useful across many different failure descriptions, not just the ones textually similar to this one.
  5. Return. The resulting parts are ranked and sent to the technician for confirmation.

Data volume, tested vs. production

Tested so far against a pool of 2,077 dispatches (dispatch_2k_rootcauses). The full historical pool this is built to cover is 1,551,773 eligible dispatches, FieldJetXStg's own measured count. Every dispatch adds one entry to the index as it completes; the rest of the 1.5 million never need to be re-embedded to add that one new record.

What retrieval actually costs, measured

Two different things affect speed, and they don't behave the same way. Tested directly at the real production scale, 1,551,773 vectors: a top-10 query averaged 122 milliseconds, top-100 averaged 348 milliseconds, top-200 averaged 601 milliseconds. Asking for more matches costs real, measurable time. An earlier version of this document assumed that cost was close to flat. It isn't, and that correction is exactly why Section 04 blends in a cheap fixed term instead of simply retrieving more matches to get the same lift.

Corpus size, on its own, matters far less. A smaller 50,000-vector index answered the same top-10 query in 0.78 milliseconds. Scaling the index up 31 times, to 1.55 million, should raise that time by a small, bounded amount, the way this kind of search is built to behave, not the roughly 157 times actually measured. That gap points to the test machine, 8 CPU cores and 8GB of memory, running low on memory at this scale, not the search itself getting that much harder. Confirming real numbers on properly sized Azure infrastructure is the first item in Section 05.

Building the full 1.55-million-vector index from scratch, on that same test machine, took 3 hours and 41 minutes, and slowed sharply as memory filled up. This is exactly why the design adds one dispatch at a time as it completes, rather than rebuilding the whole index. A full rebuild is expensive; a single new entry is not.

03

The Test That Removed the Case Pipeline

The original version of this design used the case-clustering pipeline as a scoring shortcut: match a new dispatch to a case, then use that case's history as evidence. Before finalizing anything, that design was tested against the plainest possible alternative: skip the case step, just retrieve more matches directly, and see which one actually predicts the right part more often.

ApproachUses the case pipeline?Top-6 hit rate
Guess the most common parts overallNo36.2%
Case-matched evidence, the earlier designYes39.6%
Direct search, top 10 matches, no case stepNo27.2%
Direct search, top 100 matches, no case stepNo42.3%
Direct search, top 200 matches, no case stepNo44.2%

All five rows tested on the same 265 dispatches with a real recorded part, from dispatch_2k_rootcauses. Retrieving only 10 matches without a case step performs worst of all, which is why case-matching looked necessary at first. Widening the search past 100 matches beats the case-matched design outright, without touching the case pipeline at all.

Ten matches wasn't enough evidence on its own, so routing through the case pipeline looked like the fix. It wasn't the only fix. Retrieving more matches directly solved the same problem more simply, and won. The case-clustering pipeline adds a sequential, rate-limited step to reach that evidence; a wider direct search reaches better evidence without it. This system's live path no longer uses the case pipeline at all.

One more real question came up before finalizing: root cause and parts needed are not the same thing. Two dispatches can share a root cause but need different parts, because the units differ. Two dispatches can have different root causes but need the same common part. The first case is already handled by returning a ranked list of up to six parts instead of one forced answer. The second case was worth checking directly.

ApproachTop-6 hit rate
Direct search, top 100, closeness only42.3%
Direct search, top 100, plus overall part popularity44.2 to 44.5%
Direct search, top 200, closeness only (double the retrieval cost)44.2%

Blending in how common a part is across the whole history, not just among the textually similar matches, recovers exactly the parts that are useful regardless of which specific failure was described. It matches the accuracy of retrieving twice as many matches, without the extra retrieval cost measured in Section 02. That blend is now part of the design.

One more assumption was checked rather than left standing: does the historical corpus actually need the cleaned extraction, or would the untouched dispatch-reason field embed just as well?

ApproachTop-6 hit rate
Direct search, top 100, cleaned extraction42.3%
Direct search, top 100, raw dispatch-reason field26.4%
Direct search, top 200, raw dispatch-reason field28.7%

Embedding the raw field scores below even the naive baseline (36.2%) at every retrieval width tested. The two embeddings agree on only 6.8% of their top-100 matches for the same query, on average. The raw field mixes work-order metadata, tracking numbers, assignment codes, dollar amounts, into the same block of text as the actual complaint, and that noise dominates the embedding. Cleaning the text first, the step the case pipeline already performs, is not a convenience being carried over. It is most of where this design's accuracy comes from.

04

Key Decisions and Evidence

DecisionReasoningEvidence
Search dispatch history directly; no case-clustering step in the live path A wider direct search reaches better evidence than routing through the case pipeline, without its sequential, rate-limited processing. Section 03: direct search at 100+ matches scored 42.3 to 44.2% top-6 hit rate, against 39.6% for the case-matched design it replaced.
Retrieve 100 matches per query, not 10 10 matches is too thin a pool. Real recorded parts are rare enough (see below) that a bigger pool is needed to find enough of them. Section 03: top-10 direct search alone scored 27.2%; top-100 scored 42.3%, on the same 265-dispatch test.
Blend in overall part popularity alongside closeness, not closeness alone A part that's useful across many different failure descriptions can be under-weighted by similarity search alone, since that search only looks at textually similar dispatches. Section 03: adding a fixed, precomputed popularity term to the top-100 search raised top-6 hit rate from 42.3% to between 44.2% and 44.5%, matching top-200 alone at roughly half the retrieval cost measured in Section 02.
Build the index off the notes-derived extraction the case pipeline already produces The dispatch-reason field is usually just what the ticketing system spat out. The actual diagnosis lives in the technician's notes. Already running in production for the case pipeline, so the extraction step is reused, not rebuilt. Tested directly, not just assumed: embedding the raw dispatch-reason field instead of the cleaned extraction scored 26.4% at top-100, below the 36.2% naive baseline, against 42.3% for the cleaned extraction on the same dispatches (Section 03).
Accept the technician's live description as-is at query time Running every query through an extraction step first was considered. Most queries don't need it. Checked 2,000 dispatch records pulled from FieldJetX by hand. One example, "OnCallRegion: St. Louis, MO," is a routing tag, not a description. Most looked like "BACKROOM > REFRIGERATION: Rack 00737390: Communication failure" instead, usable on its own. 83% matched that second pattern; the other 17% get caught by a plain pattern check, no model call needed.
Use bge-m3 for production; tested so far with nomic-embed bge-m3 is built for exactly this kind of match, a short live description against a longer historical record, and it's the model named in the approved plan. nomic-embed is what the case pipeline already had cached, useful for testing the mechanism early. Every number in Section 03 was produced with nomic-embed. Swapping in bge-m3 and re-running the same test is a Section 05 next step.
Azure AI Search as the vector store Other teams already run it against far more data than this corpus will ever hold. Query cost does depend on how many matches are requested, which is exactly why the design retrieves a bounded 100 and blends in a cheap popularity term instead of retrieving more. Section 02: measured 348 milliseconds average at top-100 versus 601 milliseconds at top-200, at the real 1,551,773-vector scale. Confirming these numbers on Azure's own infrastructure, not a local test machine, is a Section 05 next step.
A technician confirms every prediction before it counts A wrong guess that gets accepted silently becomes bad evidence for the next prediction, and that problem snowballs. Matches what's already approved for this use case: a suggestion a person still has to act on.
05

What's Next

Three concrete steps, each tied to something specific above. Dropping the case pipeline from this system's live path also drops what would have been a fourth: there is no separate case-to-parts feed left to build and maintain.

  • 1. Re-run the Section 03 accuracy test at full corpus scale. 100 and 200 matches, and the popularity blend, were tuned against a 2,077-dispatch pool; the best settings at 1,551,773 real dispatches may land somewhere else, once that much real labeled data exists.
  • 2. Swap nomic-embed for bge-m3, the production embedding model, and re-run that same test with it.
  • 3. Confirm the Section 02 latency numbers on Azure AI Search's own infrastructure. The local test machine used for those numbers likely ran low on memory at 1.5 million vectors, exactly the kind of gap a properly sized deployment needs to close before those numbers are quoted as production figures.

Worth knowing while these are underway: only one in five dispatches, across the whole business, has any part recorded against it at all (from case_parts_dataset, the file that first surfaced this). That scarcity is exactly why retrieval needs to be wide: a narrow pool of 10 matches rarely contains enough of the one-in-five that actually have data to learn from, which is the root cause of the low top-10 score in Section 03.

06

Recommendation

Don't turn this on for the whole corpus at once. Start on the dispatch history already cleaned and indexed today. Then extend to the rest of the historical corpus once the retrieval width and embedding model are re-tuned at full scale (Section 05).

Every decision in Section 04 traces to a measured number, a test run against a named file, or a spec that already has sign-off. Section 05 lists exactly what's left, in order.
